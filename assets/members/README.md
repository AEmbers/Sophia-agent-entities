## 二、独立复核结论（我方实测，非采信原 readme 自述）

原素材包 readme 自称的结论，我用**独立脚本**复核如下（改动未采纳任何原脚本逻辑）：

| 校验项 | 原 readme 自述 | 我方实测 | 结论 |
|---|---|---|---|
| 512 数量 | 20 | 20 | ✅ 一致 |
| 512 尺寸 | 全部 512×512 | 全部 512×512 | ✅ 一致 |
| 通道格式 | 全部 Format32bppArgb | 全部 Format32bppArgb | ✅ 一致 |
| 四角透明度 | 全部 A=0 | 全部 A=0 | ✅ 一致 |
| 中心不透明度 | 全部 A=255 | 全部 A=255 | ✅ 一致 |
| 512 总体积 | 10.2 MB | 10.2 MB | ✅ 一致 |
| 水印已清除 | 95.8% 笔画透明，余 4.2% 为红衣边缘 | 右下角放大目视：纯透明，仅衣摆红边入区 | ✅ 一致 |

**水印复核方法**：把 512 右下角 160×160 区域放大 4 倍叠在棋盘格上目视。
结果：圆角外与圆角内**均无半透明水印残留**，进入该区域的彩色像素只有人物衣摆红边
—— 与原 readme 第 59 行「余下 4.2% 为所有图共有的同一坐标，经查证是红衣服边缘而非水印」**独立吻合**。

> 复核过程中的一次无效测量（已作废）：初次用固定矩形采样框统计右下角非透明像素，
> 20 张全部得到**同一个数字**（1974）。同一数字出现在 20 张不同图上，说明量到的是
> **蒙版边缘**这一共同属性，而非水印。改用「蒙版几何外沿 + 缩放目视」后才得到有效结论。
> —— 记在这里是因为：**20 张给出同一个数，本身就是"测量口径错了"的强信号**，不要当成通过。

## 三点五、尺寸适配决策（2026-09-20，含实测）

**决策：小尺寸（含 24px 侧边列表）直接用 `out-512/` 原样缩放，不转 SVG、不新增自绘差分。**

背景：曾设想把 20 张转成分层 SVG 以便小尺寸更清晰。实际实测（VTracer 1.0.0-alpha.4）结论：

| 方案 @24px | 观感 | 体积 | 结论 |
|---|---|---|---|
| **PNG 原样** | ✅ 主色/道具/背景可分辨 | 571 KB | **采用** |
| PNG + 锐化 | ⚠️ 面部起噪点 | — | 不采用 |
| SVG（精度6，近无损） | ⚠️ 脸部发灰发平 | **797 KB（1.20×）** | **比 PNG 更糊** |
| SVG + 锐化 | ⚠️ 救不回 | — | 不采用 |

**为什么不转 SVG**：

1. 无损档 SVG 比原 PNG **更大**（797 KB vs 571 KB）。
2. 输出 `<g>` 分组 = **0**、`<path>` = **1,757** —— **没有图层结构**，
   颜色写死在每条路径上 ⇒ 无法换色、无法复用底胚。
3. 24px 下实测**比 PNG 更糊**（转档把细腻渐变简化为色块，锐化无法补救）。

⚠️ **重要副产品：缩小后位图"糊不糊"取决于内容密度，不是格式**。
同样 24px，`C 头肩裁切` 的边缘能量 **59.90** 反而低于 `A 直接降采样` 的 **82.31**——
说明"裁切后再缩"与"整图缩"是两条不同的路，不能想当然。

### 三条实现硬约束（实测得出）

1. **底部烧入的职位名在 24px 下不可读**（糊成一条灰带）
   ⇒ 小尺寸场景**必须另用 DOM 文本**渲染成员名，不能依赖图上烧入的字。
2. **图上标签无法改写**（白字 + 红印章压在服饰上，实测不透明像素 **94.4%**）
   ⇒ 显示名必须与图上标签一致（这是下面 §四 命名方案 C 的技术依据）。
3. **不要在客户端做二次裁切**：素材已是 1994×1994 蒙版成品，
   底部标签余量仅 15px，再裁会切到标签。

## 四、命名规范（已解决 · 2026-09-20）

**原判断"命名冲突"是我的误判，已修正。**

关键区分：素材上的 `灵台郎`、`推步主事` 是**职位名**（position），不是成员名。
职位名本就不该带品牌前缀（如同"架构师"不该叫"某某架构师"）。

经主人确认后，采用**三层标识模型**（已写入 `docs/REQUIREMENTS.md` FR-5A / FR-8）：

| 层 | 例子 | 唯一性 | 是否烧进图 |
|---|---|---|---|
| **职位** `position` | `灵台郎`、`推步主事` | ❌ 可多实例 | ✅ 图上印的就是它 |
| **成员名** `name` | `灵台郎`、`灵台郎-2` | ✅ 团队内唯一 | ❌ DOM 文本渲染 |
| **成员 ID** `memberId` | `sophia-lingtai-lang-a1b2c3d4` | ✅ 全局唯一 | ❌ 不可见 |

**关键收益**：显示名优先用职位名，重名时才追加序号 ⇒
「图上印的字」与「界面显示的字」**永远一致**，不会出现「图上灵台郎、旁边写 Sophia灵台郎」的割裂。

**同职位多实例**：职位可复用，成员名加序号区分。对应需求「一个子 Agent 创造的一群里，
包含和他一样职位的成员」—— 图上都印 `灵台郎`，系统内是 `灵台郎` / `灵台郎-2`。

## 五、梯队与双模调度的关系

素材的 4 梯队恰好能承载双模框架：

- **持久团队模式**：启用第一梯队（总控）+ 需要长期记忆的角色（典籍掌事、观象访事、天象值守）
- **DAG 调度队模式**：启用第二~四梯队中可并发的执行角色（推步主事、星机校验、星文审校）
- **双模共用**：钦天监监正（团长/架构老大）、星禁掌察（安全）、灵台郎（架构）、传报主事（汇报）

这样同一套素材在两种模式下都有出场，且**同一位成员可跨模式复用**（持久团队里的
「推步主事」下派子 DAG 时，DAG 里仍是「推步主事」），符合 FR-5 嵌套调度语义。

## 六、素材处理参数（可复现）

- 蒙版窗口：`x 27..2020` / `y 36..2029`（1994 × 1994 正方形）
- 圆角半径：370 px
- 边缘抗锯齿：1.5 px 线性过渡
- 512 降采样：HighQualityBicubic + HighQualityCompositing + HighQuality PixelOffset
- 垂直不居中的原因：原图内容整体偏下，实测标签最下沿 y=2014；若垂直居中则下边界落在 y=2020，仅剩 6px 余量，视觉贴边
