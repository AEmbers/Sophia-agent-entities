# Sophia-agent-entities 需求书

> 版本：v0.1（草案）
> 日期：2026-09-20
> 状态：待评审

---

## 1. 项目背景

上游存在两个各自独立的 DSH 多智能体插件：

| 上游仓库 | 并入目录 | 范式 | 强项 | 短板 |
|---|---|---|---|---|
| `wowyuarm/dsh-agent-team` | `dsh-agent-team/` | 持久团队 | 常驻角色、长期记忆、上下文接力、频道协作 | 缺少细粒度依赖编排与自动化质检门禁 |
| `NanmiCoder/dsh-agent-teams` | `dsh-agent-teams/` | 队长 DAG 战队 | 目标拆解、DAG 拓扑调度、质量门禁、活动面板 | 会话级一次性战队，缺跨项目持久记忆与常驻团队感 |

本仓库 `Sophia-agent-entities` 不是二者的简单合并，而是要在二者之上**新建一个统一框架**：以持久团队为底座、以 DAG 编排为突击手段，并在**人类审批点**把两种调度方式的选择权交给人类。

## 2. 目标与非目标

### 2.1 目标

- G1 一套插件（单 Cordis 插件）同时承载「持久团队」与「DAG 调度队」两种调度范式。
- G2 在 `StagingPlanEditor` 阶段**同时**产出两份草案（Team 草案 + DAG 草案）。
- G3 人类在 `Approve & Run` 处单选模式；**默认持久团队**，可切 DAG 调度队。
- G4 DAG 调度队的活动与结果投影到与持久团队一致的 UI（同一活动面板 + 依赖树画布），保留必要差异。
- G5 持久团队成员可把某条任务**下派**为嵌套子 DAG 攻坚。
- G6 全成员类型（常驻 / 临时 / DAG）支持中途热换模型。
- G7 DAG 团队归属权严格隔离，未授权禁止插手。
- G8 全成员类型支持中途回收（suspend）与销毁（destroy）。
- G9 全成员命名强制合规 `Sophia + 中文`。

### 2.2 非目标（本期不做）

- N1 不改写上游两个仓库的原始代码（只做 `git subtree` 收录与只读参考）。
- N2 不实现跨机器的分布式调度（单进程 / 单 DSH 实例内）。
- N3 不自研模型层，模型能力完全复用 DSH 宿主已注册的 provider/model。
- N4 不做移动端原生客户端。

## 3. 功能需求

### FR-1 双模草案生成

- FR-1.1 用户以自然语言提出需求后，系统须一次性生成 `StagingDualPlan`，含 `teamPlan` 与 `dagPlan` 两部分。
- FR-1.2 `teamPlan` 须给出：目标频道、拟指派常驻成员、拟拆分的 TaskThread 列表。
- FR-1.3 `dagPlan` 须给出：动态成员 roster（角色 + 模型 + 数量）、带依赖关系的任务 DAG。
- FR-1.4 两份草案在同一面板内可切换预览，且均以「未执行」状态存在，不得自动开工。

### FR-2 人类核准与模式路由

> ⚠️ **本系统的「审批」共有两处，不要混淆**：
> - **审批点 ①（本节）**：窗口会话向人类呈送**双模草案**时的核准 —— 决定「这批活走持久团队还是 DAG 调度队」。
> - **审批点 ②（FR-5.3）**：**成员要开持久团**时的两级审批 —— 团长预审 + 推送人类收件箱。
>
> 两者都是人类把关，但**时机、对象、通道**不同：① 在需求入口，② 在运行期的资源扩张点。

- FR-2.1 提供单一核准动作 `Approve & Run`，模式选择项默认值为 `persistent-team`。
- FR-2.2 选择项支持 `persistent-team` / `dag-scheduler` 二选一。
- FR-2.3 核准事实须落账本（操作者、时间、planId、选中模式）。
- FR-2.4 只有发生核准之后，调度器才允许派发任务。
- FR-2.5 核准动作由**窗口会话（宿主）**呈送；同一个团可被任意窗口呈送核准与下达任务。

### FR-3 持久团队范式

- FR-3.0 **角色**：持久团设**团长（Principal）**一名，由团内成员担任（如钦天监监正），
  对该团的技术决策负责，并承担 FR-5.3 的第一级审批职责。
- FR-3.1 成员具备持久身份：`memberId`、专属 `sessionId`、私有记忆路径。
- FR-3.2 成员具备生命周期状态：`active`（在岗）/ `suspended`（可逆挂起，见 FR-9.1）/ `archived`（终态，见 FR-9.3），
  以及存在态 `idle` / `running`。
  > **修订（2026-09-23，依 SPEC-sophia-core 裁决 Q-C）**：原 `inactive` 与 FR-9.1 的 `suspended` 是同物异名，
  > 现合并为 `suspended`（规范名取 FR-9.1，因其有明确的可逆操作对 suspend/resume 定义；
  > 而 `inactive` 仅有名称、无定义转换）。
- FR-3.3 任务在频道内以 Task Thread 推进，支持认领、交接、人类验收。
- FR-3.4 上下文支持 rollover / checkpoint，切换与重启不丢待决事项。
- FR-3.5 团的存续**不依赖任何窗口会话**：窗口关闭后，团由常驻调度体继续驱动（FR-5.0.5）。

### FR-4 DAG 调度范式

- FR-4.1 任务具备显式状态机，依赖未完成的任务不可被认领。
- FR-4.2 支持质量门禁链：需求 → 实现 → 验证 → 评审 → 集成。
- FR-4.3 门禁未过须能自动生成修复任务并重新评审。
- FR-4.4 DAG 执行过程须投射到活动面板（进度分段条、成员卡片、阻塞提示）。

### FR-5 团队派生、角色模型与审批门

> **本节是 `Sophia-agent-entities` 的核心自有设计，上游两项目均无此概念。**
> 上游把团队绑死在窗口会话 ID 上（`dsh-agent-teams/src/types.ts:248` 的 `captainSessionId`），
> 后果是窗口一关团队就变成「占着资源却办不了事」的僵尸团。本节从根上解决它。

#### FR-5.0 角色模型（先定清楚，后文全部依赖它）

以「皇帝下旨」为喻：

| 喻体 | 系统角色 | 术语 | 是否绑定会话 |
|---|---|---|---|
| 皇帝 | 人类用户 | `Human` | — |
| **传旨小秘** | **当前窗口会话**（可随时更换） | `Host`（宿主/信使） | ❌ **不绑团** |
| **监正** | **持久团团长**（架构老大） | `Principal`（团长） | ✅ 绑在团上，**是团内成员** |
| 百官 | 团内普通成员 | `Member` | ✅ 绑在团上 |

**核心原则**：
- FR-5.0.1 **团队是独立实体**：有自身 `teamId` 与生命周期，**不归属于任何窗口会话**。
- FR-5.0.2 **团长是团内成员**：持久团团长（如钦天监监正）是团的一员，**不是**窗口 Agent。
  监正在设定上是「架构的老大」，对该团的技术决策负责。
- FR-5.0.3 **窗口是宿主 / 传旨通道**：任意窗口可向任意持久团下达任务；
  窗口关闭**不影响**团队存续与运转。
- FR-5.0.4 **代孕创建**：窗口创建团的壳（拿到 `teamId`）→ 以团的名义生成首任团长 →
  完成后窗口与团**解耦**。窗口是产房，不是爹。
- FR-5.0.5 **常驻调度**：团须有不依赖任何窗口的调度体，才能在无人对话时唤醒成员干活。

#### FR-5.1 团队二分

- 团队分**持久团**（跨会话存续、成员带长期记忆）与**临时团**（任务组，完成即回收）两类。
- 临时团短命：所属任务完成即自动回收。
- 持久团跨会话存续，不随任务结束而回收；停下须显式走 FR-9 的挂起/销毁。

#### FR-5.2 派生权限矩阵

| 发起方 | 可开持久团 | 可开临时团 |
|---|---|---|
| 持久成员 | ✅（**需人工批准**，见 FR-5.3） | ✅（自动批准） |
| 临时成员 | ❌ | ✅（自动批准） |

- FR-5.2.1 临时成员**无权**创建持久团；尝试时须明确拒绝并说明原因。
- FR-5.2.2 **深度不设硬性层数上限** —— 控制手段是「审批门」而非「深度闸」。
  每开一层持久团都要过一次人工批准，因此可嵌套而不会失控。

#### FR-5.3 持久团创建的两级审批

成员发起创建持久团时，须**依次**通过两级：

```
成员发起 → ① 团长（监正）预审 → ② 推送到人类收件箱 → 人类批准 → 创建
                    ↓ 不通过                ↓ 不批准
                  打回并说明理由          不创建（成员不得降级为临时团绕开）
```

- FR-5.3.1 **第一级 · 团长预审**：由该成员所属团的团长（监正）审核。
  目的：避免人类被大量申请淹没，同时让「架构老大」对技术决策负责。
- FR-5.3.2 **第二级 · 人类批准**：团长通过后，审批请求**推送到人类收件箱**
  （沿 `dsh-agent-team` 已有的 Human Inbox 机制，使「任意窗口都能看到待办」）。
- FR-5.3.3 人类批准须落账本（申请成员、目标团规格、两级审批人、时间、结论）。
- FR-5.3.4 **不得绕开**：未获批准时，**不允许**该成员降级为「先开个临时团凑合」。
  否则「需要批准」将形同虚设。
- FR-5.3.5 成员开**临时团**无需任何审批，直接执行。

#### FR-5.4 子团归属

- FR-5.4.1 子团归**发起的那个成员**个人所有，**只服务他的专属任务**，
  不是整个上级团的公共资产。
- FR-5.4.2 子团的归属者（owner）对其拥有完整调度权；他人未获显式移交不得插手（见 FR-7）。

#### FR-5.5 嵌套调度

- FR-5.5.1 持久团队成员可对某条具体任务发起子 DAG 攻坚。
- FR-5.5.2 子 DAG 完成后须把结果写回原任务的 Task Thread，形成闭环。
- FR-5.5.3 子 DAG 的归属者默认为发起该次下派的成员。

#### FR-5.6 父成员消失时的子团处置

- FR-5.6.1 子团**转挂到最近的存活祖先**（默认），不级联销毁（保工作成果），
  不冻结（免僵尸团）。
- FR-5.6.2 若无可转挂的祖先，则转挂到该团团长（监正）名下。
- FR-5.6.3 转挂事实须落账本。

### FR-5A 成员标识三层模型

> 因素材图的职位标签已烧入像素（无法改写），标识必须分层。

- FR-5A.1 **职位（position）**：如 `灵台郎`、`推步主事`。**不唯一**，同职位可多实例。
  素材图上印的就是这一层。
- FR-5A.2 **成员名（name）**：团队内**唯一**。默认与职位名相同；
  同职位多实例时追加序号（`灵台郎-2`、`灵台郎-3`）。
- FR-5A.3 **成员 ID（memberId）**：全局唯一，形如 `sophia-<position-slug>-<uuid8>`，界面上不展示。
- FR-5A.4 界面显示名**优先用职位名**，仅在重名需要区分时露出序号，
  以保证「图上印的字」与「界面显示的字」始终一致。
- FR-5A.5 职位名**不要求** `Sophia` 前缀（见 FR-8 修订说明）。

### FR-6 动态换模

- FR-6.1 人类可在成员卡片上直接切换该成员所用模型。
- FR-6.2 插件/成员自身可基于策略（上下文压力、质检连续失败、任务复杂度）申请换模。
- FR-6.3 换模须支持**运行中热切**：不重启成员、不重建会话。
- FR-6.4 换模须落账本审计（成员、旧模型、新模型、触发原因、触发者）。
- FR-6.5 成员正忙时，换模须在最近的步骤边界生效。

### FR-7 DAG 归属权与隔离

- FR-7.1 每个 DAG 团队实例须带 `dagTeamId` 与 `ownerMemberId`。
- FR-7.2 非 owner 的成员对该 DAG 团队的任何读/写/派发操作须被拒绝并明确报错。
- FR-7.3 任务未显式声明「申请移交某 DAG 归属」时，一律为该成员新建独立 DAG 团队。
- FR-7.4 归属移交须由当前 owner 发起，成功后新 owner 获得完整调度权，全过程落账本。

### FR-8 命名规范

> **修订说明（2026-09-20）**：原 FR-8 要求"全成员命名须带 `Sophia` 前缀"，
> 该规则**管错了对象** —— 素材图上的 `灵台郎`、`推步主事` 是**职位名**，不是成员名。
> 职位名本就不该带品牌前缀（如同"架构师"不该叫"某某架构师"）。
> 且职位标签已烧入素材像素（实测不透明像素占比 94.4%），无法改写。
> ⇒ 本条按 FR-5A 的三层模型重写。

- FR-8.1 **职位名（position）**：使用中国古代天文机构职官体系（钦天监 / 灵台 / 推步 / 历算），
  纯中文，**不要求** `Sophia` 前缀。须与素材图上的烧入标签**逐字一致**。
- FR-8.2 **成员名（name）**：默认等于职位名；重名时按 FR-5A.2 追加 `-<序号>`。
  成员名在团队内须唯一，重复创建须被拒绝并提示可用的序号。
- FR-8.3 **成员 ID（memberId）**：须带品牌前缀，格式 `sophia-<position-slug>-<uuid8>`，
  其中 `position-slug` 为职位的拼音转写（如 `灵台郎` → `lingtai-lang`）。
- FR-8.4 命名校验对人工输入与模型自生成**一视同仁**；不合规须在创建/重命名入口拒绝，
  且错误信息须说明规则与正确示例。
- FR-8.5 除成员 ID 的 `sophia-` 前缀外，**对用户可见的任何名称不得出现英文字母**
  （唯一例外：索菲亚自身的英文名 `Sophia`）。

### FR-9 生命周期管控

- FR-9.1 任一成员支持中途挂起（suspend）：保存断点、释放运行时句柄、状态置 `suspended`。
- FR-9.2 任一成员支持恢复（resume）：从断点重建运行时。
- FR-9.3 任一成员支持彻底销毁（destroy）：强制打断当前轮次、清理私有存储、账本打墓碑。
- FR-9.4 挂起与销毁须即时反映到前端成员列表与活动面板。

### FR-10 统一账本与投影

- FR-10.1 所有协作事实（频道、成员、任务、消息、核准、换模、归属移交、生命周期）须只追加写入 SQLite 账本。
- FR-10.2 前端所有视图（频道流、活动面板、依赖树、收件箱）须为账本事实的投影，不得持有独立真相。
- FR-10.3 须支持按 scope 增量拉取变更，避免全量刷新。

## 4. 非功能需求

| 编号 | 需求 | 验收口径 |
|---|---|---|
| NFR-1 | 可观测性 | 每次派发、换模、移交、销毁均可从账本回溯出完整时间线 |
| NFR-2 | 隔离性 | 跨 DAG 团队的数据与调度权互不可见、互不可扰 |
| NFR-3 | 兼容性 | 作为单个 Cordis 插件挂载，不破坏未安装该插件的普通 Session |
| NFR-4 | 可回滚 | 成员销毁后其账本记录仍可审计（墓碑 + 历史） |
| NFR-5 | 本地化 | UI 文案跟随 DSH 官方 locale 服务，支持中英实时切换 |
| NFR-6 | 性能 | 100 节点级 DAG 的画布渲染与交互须保持可用 |

## 5. 约束

- C1 宿主为 DeepSeek Harness，插件须遵循 Cordis 插件规范。
- C2 仓库以 `git subtree` 收录上游，不得改为 fork 或 submodule。
- C3 成员对外可见名称必须符合 FR-8；内部 ID 不受此约束。
- C4 所有破坏性操作（销毁、归属移交）必须留审计痕迹。
